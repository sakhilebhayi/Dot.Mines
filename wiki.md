# Dot.Mines

Purpose: this is the Mines platform's own knowledge home — owned and maintained by the platform team, written in its own voice. It describes what this codebase actually is today, what it emits, and how it plans to connect to the wider Dot Ecosystem. Dot.Brain never edits this file; it only reads what we choose to publish.

> **Related:** [Dot.Brain's ingested view of this platform](https://github.com/sakhilebhayi/Dot.Brain/blob/main/platforms/dot-mines.md)

## 1. What Dot.Mines Is

Dot.Mines (repo name: `mines`) is a fleet management and mining-operations platform: real-time GPS machine tracking, geofencing, maintenance and fuel management, production tracking, OEM telemetry integrations, and a multi-agent AI optimization layer, built for open-pit mine operators, dispatchers, supervisors, and operators.

**Status:** this is a real, working Laravel 12 application — not a blueprint. The `README.md` describes it as "production ready" and it ships a substantial feature set: live map, operations feed (a structured replacement for WhatsApp shift comms), maintenance booking, fuel budgets, route planning, IoT sensor ingestion, Stripe billing, and team-based multi-tenancy. OEM manufacturer integrations exist as a service layer (25 manufacturer classes) but no manufacturer connection has been verified against a real account — see §5.1. This wiki describes what is actually implemented; anything not yet built is called out explicitly under Roadmap (§7).

## 2. Architecture (as implemented)

| Layer | Technology |
|---|---|
| Backend | PHP 8.2+, Laravel 12.x |
| Frontend | Livewire 3.x, Alpine.js 3.x |
| Database | PostgreSQL 16+ |
| Styling | Tailwind CSS 3.x, DaisyUI 5.x |
| Charts | ApexCharts 5.x, Chart.js 4.x |
| Maps | Leaflet 1.9.x + Leaflet Draw, OpenStreetMap / Esri World Imagery |
| Real-time | Laravel Reverb (WebSockets), Laravel Echo, Pusher.js |
| Queue | Laravel Queue (database driver) |
| Auth | Laravel Jetstream + Sanctum, team-scoped sessions |
| Payments | Stripe via Laravel Cashier |
| File storage | AWS S3 via Flysystem |
| Search | Laravel Scout |
| Error monitoring | Sentry |
| Static analysis / tests | PHPStan, Psalm, PHPUnit 11 |

Multi-tenancy is team-based: each mine operates as an isolated `Team`, with role-and-policy-scoped data access (`HasTeamFilters` trait, `AuthServiceProvider` policies for Machines, Alerts, Geofences, Integrations, Notifications, Reports, Teams). Roles observed in the codebase: Operator, Supervisor, Safety Officer, Manager, Admin.

AI features run as a set of specialist services under `app/Services/AI/`: `FleetOptimizerAgent`, `MaintenancePredictorAgent`, `FuelPredictorAgent`, `RouteAdvisorAgent`, `CostAnalyzerAgent`, `AnomalyDetectorAgent`, orchestrated by `AIOptimizationService`. Recommendations are logged and can be accepted or dismissed (`AiRecommendationAction`), which is the closest existing analogue to an audit trail for AI-driven decisions.

OEM telemetry integrations live under `app/Services/Integration/` — one service class per manufacturer (25 total: CAT, Komatsu, Volvo, Sandvik, Epiroc, Liebherr, Hitachi, Hyundai, John Deere, Doosan, JCB, Bobcat, Kawasaki, Kobelco, Yanmar, Kubota, XCMG, CASE, New Holland, Atlas Copco, Bell, Sany, Takeuchi, Roundebult, CTrack), all implementing a common `ManufacturerServiceInterface` via `BaseManufacturerService`. Ingestion is poll-based — a scheduled job (`SyncIntegrationMachinesJob`) calls each manufacturer's REST API on an interval — not webhook-based; `WebhookController` exists only for inbound Stripe billing events, unrelated to telemetry. Credentials are stored per-team, encrypted at rest (`Integration.credentials` uses Laravel's `encrypted:json` cast as of this pass — it was a plain `json` column before, despite the UI already claiming "encrypted and stored securely"), and never exposed in API responses. **No manufacturer connection has completed a live sync against a real account**: 8 of the 25 (John Deere, CASE, New Holland, Takeuchi, Bobcat, Yanmar, Atlas Copco, Sandvik) honestly report "coming soon" rather than faking a successful connection; **Bell** is now built against Bell Equipment's own published ISO 15143-3 (AEMP 2.0) API spec and Postman collection (real OAuth2 token exchange, real endpoint paths, XML parsing, 12 passing unit/integration tests) but has not yet completed a confirmed live sync; the other 16 have a service class that attempts real HTTP calls to endpoints inferred from public docs, but those endpoint shapes have not been confirmed end-to-end against real credentials, and the `integrations` table has zero rows from any real team as of this writing.

## 4. Events It Emits

All are `ShouldBroadcast` Laravel events, broadcast in-app over Reverb/WebSockets — these are internal real-time UI events today, not yet published as cross-platform Knowledge Packs:

| Event | Trigger |
|---|---|
| `MachineLocationUpdated` | GPS position update |
| `MachineOffline` | Machine stops reporting |
| `GeofenceEntryDetected` / `GeofenceExitDetected` | Machine crosses a geofence boundary |
| `AlertTriggered` | Any alert condition fires |
| `MaintenanceAlertTriggered` | Health-trend-based predictive maintenance alert |
| `ComplianceViolationDetected` | Compliance violation logged |
| `SensorReadingRecorded` / `SensorStatusChanged` | IoT sensor telemetry |

Supporting background jobs (`app/Jobs/`) that produce these events include `MachineLocationUpdateJob`, `MachineIdleMonitoringJob`, `MachineStatusMonitoringJob`, `GeofenceCrossingDetectionJob`, `RouteSpeedMonitoringJob`, `AlertGenerationJob`, `SyncIntegrationMachinesJob`, and `SyncMachineMetricsJob`.

**What is real and working today, independent of any manufacturer:**
- Credential storage (`Integration.credentials`, encrypted at rest as of this pass, never returned in API responses)
- Team-scoped CRUD for integration records (`Api\IntegrationController`)
- Sync jobs (`SyncIntegrationMachinesJob`, `SyncMachineMetricsJob`, `MachineLocationUpdateJob`, `MachineStatusMonitoringJob`) are correctly wired and bug-fixed, and — as of this pass — `SyncIntegrationMachinesJob` genuinely runs on a schedule (`integrations:sync-due`, every 5 minutes, honoring each provider's own configured interval) instead of only firing on a manual "Sync Now" click; the other three jobs remain manual/event-triggered only. None have run against a real manufacturer response for the 16 unverified providers.
- The `machines`, `alerts`, `production_records`, and `fuel_transactions` tables this platform's *own* users populate directly (dispensing forms, manual entry) — real, live, unrelated to OEM ingestion
- For Bell specifically: real OAuth2 token acquisition/caching, real endpoint URLs, XML parsing with data-quality guardrails (lat/lon range checks, fuel 0-100% range checks), a real scheduled sync, real caution-code-to-Alert wiring, and the full `Integration → Machine → MachineMetric`/`Alert` sync pipeline — proven end-to-end against a fabricated-but-realistic XML fixture in `tests/Unit/BellServiceTest.php`, not yet against Bell's live server

**Five real, total-breakage bugs found and fixed while building the Bell integration** (all pre-existing, affecting every manufacturer, not Bell-specific):
1. `IntegrationManager::createIntegration()` pre-`json_encode()`'d the `credentials`/`config` arrays before assigning them to model attributes already cast to `json`/`encrypted:json` — double-encoding meant every `->credentials` read back a PHP string instead of an array, everywhere, for every provider, every time.
2. `integrations.api_key`/`api_secret` were `NOT NULL` columns with no default that nothing in the app has read in years (every real service reads `credentials` instead) — but `createIntegration()` never set them, so **every single "Add Integration" submission through the real UI, for any of the 25 providers, has always thrown a database error**, silently swallowed and shown as a generic "Failed to create integration. Please try again." toast.
3. `IntegrationService::syncMachines()` iterated `$service->fetchMachines()`'s raw return value directly instead of unwrapping its `['machines']` key — the very first "machine" synced on every call, for every provider, was actually the boolean `success` flag, fatalling instantly. This is the method behind the "Sync Now" button and the scheduled `SyncIntegrationMachinesJob`; it had never been exercised with a manufacturer response reaching this far before.
4. Nothing scheduled `SyncIntegrationMachinesJob` (or any sync job) for any of the 25 manufacturers — sync only ever happened via a manual "Sync Now" click or a direct API call, despite every manufacturer config declaring its own `sync_interval`. Fixed with a new `integrations:sync-due` command, scheduled every 5 minutes, that dispatches each connected integration only once its own configured interval has actually elapsed.
5. `fetchMachineAlerts()` (each manufacturer's fault/caution-code fetch) has existed on `ManufacturerServiceInterface` since it was written, but `IntegrationService::syncMachines()` never called it — only alerts already inline in `fetchMachines()`'s response were ever synced, which for Bell (and likely others, by the same ISO-style design of a separate current-status vs. fault-code call) is always empty. Real fault codes never reached the `alerts` table for any provider. Fixed: `syncMachines()` now calls `fetchMachineAlerts()` per synced machine.

**A sixth, this time affecting all 16 "available" (non-Bell) manufacturers specifically, found and fixed in 0.3.11 while auditing them for the same classes of bug (no real credentials for any of them exist to test against — this was a request to make the code solid regardless, not to fabricate live connections):** `SyncMachineMetricsJob`/`IntegrationService::syncMachineMetrics()` both mass-assign whatever a service's `fetchMachineMetrics()` returns directly onto a `MachineMetric` — a single flat array of its own fillable columns. Two distinct shape bugs meant this silently never worked for any of them:
- CAT, Komatsu, Volvo, and Kawasaki built a *list* of `{type, value, unit, timestamp}` readings and returned it as-is — mass-assigning a list against named columns creates an almost-empty row (just `team_id`/`machine_id`) every single time. Fixed with a new shared `BaseManufacturerService::normalizeMetricsForStorage()` helper: every reading is preserved in `raw_data` (nothing already being fetched is lost) with `recorded_at` set to the latest reading's own timestamp, rather than attempting to map each manufacturer's own invented reading "type" strings onto real columns — those names were never derived from a confirmed real API response, so guessing a mapping would trade one kind of fabrication for another.
- The other 12 (Epiroc, Hitachi, JCB, Doosan, Roundebult, Kubota, Hyundai, Kobelco, XCMG, Sany, Liebherr, CTrack) call the shared `parseMetrics()` helper 2-3 times (once per API endpoint) and combined the results with a plain `array_merge()` — since `parseMetrics()` always returns the same set of keys, only the *last* source's values ever survived; the earlier ones were silently overwritten every time. Fixed with a new `mergeMetricsPreferNonNull()` helper (keeps the first non-null value per field, unions `raw_data` instead of replacing it). Separately, `parseMetrics()` itself used `'timestamp'`/`'engine_temp'`/`'fuel_consumption'`/`'coolant_temp'` — none of which are real `MachineMetric` columns (`'recorded_at'`/`'engine_temperature'`/`'fuel_consumption_rate'`/`'coolant_temperature'` are) — renamed to match.

**A further, separately-scoped bug found but deliberately not fixed in the same pass:** `CATService::fetchMachines()` and `fetchMetrics()`'s own sub-calls check response keys (`$response['assets']`, `$diagnostics['diagnostics']`, etc.) that don't exist on `makeRequest()`'s own `{success, data, status}` wrapper — a real, internally-verifiable bug (independent of what CAT's actual API returns) that means `fetchMachines()` for CAT always returns zero machines today, and likely affects Komatsu/Volvo/Kawasaki similarly given the shared origin of these stub classes. Not fixed here: correcting it requires assuming a specific nesting depth for each fake endpoint's *own* response body, which is no longer verifiable-without-guessing the way the `MachineMetric`-column fix above was (that had this app's own real schema as ground truth; this has only an unconfirmed, guessed-at upstream API shape). Flagged rather than silently patched with another guess.

**What "ingested / stored / displayed / analysed / actionable / notifications" would require, none of which exist today:** for Bell, a real account to run "Test Connection" against and confirm the XML parsing matches reality; for the other 16, the same plus confirmation the guessed endpoint paths and field names are even correct; for all of them, a normalized telemetry model to receive the data (§3 of this directive); everything downstream of that is presently unbuilt because there is nothing real to build it against yet.

**Deliberately not built yet: a normalized "universal telemetry model" schema.** A later pass in this same platform-loop considered building one now (`Machine → Identity/Location/Engine/Fuel/DEF/Hours/...`), ahead of any real telemetry to design it against. Declined: this session already found and fixed several examples of exactly that anti-pattern already sitting in this codebase — a well-designed `Notification` model with a real API controller and zero rows because nothing ever wrote to it, a `ToastNotificationService.js` wired to a Reverb server that never runs, 17 manufacturer service classes implementing a clean shared interface against endpoints nobody has ever confirmed. Building another normalized schema now, before a single real manufacturer field mapping exists to validate it against, would add a fourth. The right trigger for this specific piece of work is a real manufacturer connection to design the mapping against — not before.

## 6. Naming Discrepancy (Open Question)

Dot.Brain's ecosystem registry refers to this platform as `dot-mines` and its knowledge doc lives at `Dot.Brain/platforms/dot-mines.md`. The actual GitHub repository is named `mines` (no `Dot.` prefix) — `github.com/sakhilebhayi/mines`. The application itself brands as "Mines — Mining Intelligence Platform" in its README, not "Dot.Mines". This wiki keeps the `Dot.Mines` branding in its title for ecosystem consistency, but the repo-name vs registry-id vs product-name mismatch (`mines` / `dot-mines` / "Mines") is unresolved and should be reconciled — either by renaming the repo, or by Dot.Brain's registry explicitly documenting the mapping.

## 8. Production Command Centre — Scope Note

The Dashboard today is honest (real zeros, no fabricated metrics, a real "Active Alerts" widget wired to the same `Alert` model the notification bell now reads) but is not yet a command centre in the sense the telemetry-loop directive means: a single view that answers *what's happening, where, why, and what to do about it* by cross-referencing production, fuel, maintenance, and alert data over time. Genuinely building that needs trend analysis across multiple real data sources at once (not just point-in-time counts), and most of its value depends on the OEM telemetry gap in §5.1 closing first — a command centre summarizing mostly-empty tables would just be an elaborate empty state. Deliberately scoped as future work rather than attempted now.
